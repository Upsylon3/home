# Your HOME server

This download runs the complete HOME server and web interface on your own
computer. No HOME subscription, GitHub login, Node, Git or compiler is needed.
The first account lives here. This release does not yet link accounts across
servers or combine their storage.

## Before starting

1. Install Docker Desktop on Windows/macOS, or Docker Engine with the Compose
   plugin on Linux: https://docs.docker.com/get-started/get-docker/.
   Windows needs Linux containers/WSL 2. Start Docker before HOME. Docker
   installation, OS permissions and any required restart remain manual.
2. Choose the download matching your processor: x64 for Intel/AMD, arm64 for
   Apple silicon or an ARM Linux machine. Windows downloads target x64.
3. Extract the complete archive into a private folder on the disk where you
   want HOME's data. Keep its contents together; avoid commas in its path.
   For an existing source Compose server, use the import section below.

Images are included, so HOME itself needs no internet connection after Docker
and this download are installed. Initial Docker installation may need internet.

## Start and claim your HOME

- **Windows:** double-click `home.cmd`. For other actions, open a terminal in
  this folder and run `home.cmd ACTION`.
- **Linux/macOS:** open Terminal in this folder and run `./home.sh`.
  If necessary first run `chmod +x home.sh`. For other actions use
  `./home.sh ACTION`.

The launcher loads the included containers, creates configuration and starts
HOME. Open **http://localhost:8080/register on this same server computer**.
Copy the temporary setup code from the launcher's output and create your owner
account. Codes expire after 15 minutes and work once. Run the `code` action for
a new code. Nobody can claim the server merely by knowing its IP address.

Open **Applications** in Home after signing in. On a fresh installation, choose
an included app and click **Install**, then **Enable**. Install and enable
HomeCloud before Media, Notes or Sync. Existing installations keep their app
registrations and disabled choices when upgraded. Uninstall keeps app data and
removes its launcher entry; services stay deployed, so saved direct app links
can still work. HomeCloud remains the protected storage foundation.

Create your owner account locally before enabling access from other devices.
Do not send setup codes through the public portal. Later, give a new code to
each household member you want to join; their accounts are regular users.
The owner can manage accounts in HOME Settings. Enable two-factor authentication
before allowing public access. HomeVault still awaits independent security
review: do not use it for real secrets yet.

**Server without a screen/browser:** from your personal computer, open an SSH
connection with `ssh -L 8080:localhost:8080 YOUR-USER@SERVER-LOCAL-IP` and keep
it open. Open `http://localhost:8080/register` on that personal computer and
use the code generated by the launcher on the server. SSH securely forwards
that local connection without exposing the setup page to the network. This
requires SSH to be enabled on the server; HOME does not enable it for you.

## Everyday actions

| Action | Purpose |
|---|---|
| `start` (default) | Start the existing installation; preserve configuration and data |
| `code` | Issue one account-creation code; invalidate the previous unconsumed code |
| `access` | Choose this computer, trusted LAN, or public HTTPS |
| `diagnose` | Check configured public DNS and the local HTTPS certificate without changing access |
| `snapshot DESTINATION` | Pause HOME, capture and verify all eight data sources, then resume previous services |
| `recover-snapshot` | Resume original services after an interrupted snapshot |
| `export-backups DESTINATION` | Copy and verify published archives to an existing mounted storage folder |
| `verify-backups EXPORT-FOLDER` | Recheck an export's inventory, checksums and restorable databases |
| `status` | See which services are running |
| `logs` | Inspect service errors; redact private information before sharing |
| `stop` | Stop HOME, keeping its data |
| `upgrade OLD-FOLDER` | Transfer a stopped managed installation into this new bundle |
| `import SOURCE-FOLDER` | Copy an existing source Compose installation into this bundle |

Containers restart when Docker starts unless stopped explicitly. On Windows
and macOS, configure Docker Desktop to start at sign-in if desired. A sleeping
or powered-off computer cannot serve HOME. These launchers do not change your
OS startup, firewall or router settings automatically.

## Other devices at home

Run `access` and select **Home network**. This explicitly enables unencrypted
HTTP on port 8080 for a trusted LAN; do not use it for HomeVault or forward it
to the internet. Find the server's local IPv4 address with `ipconfig` on
Windows, `hostname -I` on Linux, or `ipconfig getifaddr en0` on macOS Wi-Fi.
Then open `http://LOCAL-IP:8080` on a device on the same network. Allow port
8080 through the server firewall for the private network only if necessary.
Reserve the server's local IP in the router so forwarding/bookmarks stay valid.
For encrypted private access, use a private-network connection and HTTPS instead.

## Outside access without paying for HOME infrastructure

You do not need a central HOME account or paid domain. An optional free
dynamic hostname (for example https://www.duckdns.org/) can point to your
public IP and follow it when it changes. Create that provider account
yourself and configure its updater on your router or server using the
provider's instructions. This release does not store a DNS-provider token
or automatically update DNS. The provider supplies an address, not HOME login.

1. First create the owner account locally and enable its two-factor login.
2. Obtain a hostname and point it to your home connection's public IP.
   If using IPv6 DNS, ensure its address and firewall routing are correct too.
3. Reserve the server's LAN IP. In your router, forward **TCP ports 80 and
   443** to that computer; allow those ports in its firewall. **Never forward
   port 8080.** Do not disable the firewall or expose the whole computer/DMZ.
4. Run `access`, choose **Public HTTPS**, enter the hostname and confirm.
   Caddy obtains and renews the free certificate. Until DNS and incoming
   connections work, the public address will not work.
5. Turn off Wi-Fi on your phone and open `https://YOUR-HOSTNAME` using mobile
   data. A test inside the house does not prove outside access. Bookmark this
   address or save it in the HOME public portal; sign in on your server.

Run `home.cmd diagnose` (Windows) or `./home.sh diagnose` (Linux/macOS) after
starting HOME. This read-only command reports A/AAAA records using the container's
DNS resolver and checks the local TLS service's certificate chain and hostname.
It sends no login credentials or files, uses no public-IP discovery service,
and does not change DNS, router rules, access mode or installation data.
DNS lookups and the TLS handshake each have a five-second deadline.
Missing DNS, resolver errors, private/shared/reserved answers or an unverified
certificate produce exit code 1 with next steps. Local/LAN mode reports that
public HTTPS is disabled and performs no network probes. Exit code 0 does
**not** prove outside reachability or that the gateway/apps are healthy.

Compare the reported A records with your router's WAN/public IPv4 address.
If they differ, check the dynamic DNS updater. A private WAN address or one in
`100.64.0.0–100.127.255.255` suggests double NAT or provider CGNAT; it is not
conclusive proof. Ask the provider about incoming connections or check the
upstream router. If AAAA records exist, check IPv6 routing/firewall rules too.
Split DNS may return private addresses locally, so also check public DNS using
your provider's tools. Use `status` and `logs` for TLS startup/certificate errors,
then repeat the phone test over mobile data.

The wizard validates your hostname and local owner setup. It cannot establish
public reachability from inside your network, diagnose all routers/CGNAT, or
promise a certificate before the public validation succeeds. Use `logs` to
inspect certificate errors. Changing back to local or LAN access stops the
public gateway; remove old router rules yourself as well.

**If direct access fails:** some providers share public IPv4 between households
(CGNAT), or block incoming connections. A saved IP or hostname does not bypass
that. Ask whether your provider offers a public IP without charge. Alternatively,
use a personal private-network service such as https://tailscale.com/pricing
(currently a free personal plan) on the server and accessing devices. Follow its
HTTPS setup guidance. This adds a provider dependency for connectivity; HOME
accounts and files remain here. It is optional and is not bundled or activated.

Raw public-IP HTTPS is not configured by this version. A free hostname is the
supported direct-access path, allowing the existing gateway to renew certificates.

## Data, backups and recovery

- `data/` contains persistent databases, uploads and certificates.
- `configuration/` contains service credentials and installation settings.
- `backups/` receives nightly validated application snapshots, retained for
  14 days. Certificates and configuration need their own protected backup.

Keep this entire folder private: someone who can read/modify it can control
your HOME. On Windows, restrict its permissions to your OS account; container
Unix permission flags do not establish Windows access controls. Protect the
disk and backups using your operating system's encryption facilities.

Backups on the same disk do not protect against disk failure. Copy protected
backups off the machine. For a full installation copy including settings, run `stop`, copy
`data/`, `configuration/`, `compose.json` and `backups/` to protected storage,
then `start`. Preserve credentials: replacing them can break existing services
and sessions. Do not run two copies of the same installation concurrently.

### Create a coordinated snapshot

Use this for a fresh matching set of all eight application data sources. First
mount private storage accessible to Docker and create a destination outside the
installation, with enough free space for the data, archives and restore scratch.
Check the mount yourself; HOME cannot prove that it is off-machine or durable.

~~~text
Windows:       home.cmd snapshot "Z:\HOME backups"
Linux/macOS:   ./home.sh snapshot "/mnt/backup-nas/HOME"
~~~

HOME stops all containers in this installation, including gateways, backup and
optional services. Downtime lasts through capture and verification and grows
with the data size. It publishes a new `home-snapshot-...` folder only when all
eight archives pass, then starts exactly the containers that were running before.
Previously stopped services stay stopped. The capture deadline is one hour;
set `BACKUP_TIMEOUT_SECONDS` in the host shell to 1–86400 seconds if needed.
This manual action does not change the daily backup schedule or prune old sets.

Keep the set and its `manifest.json` together. Recheck it with
`verify-backups "<destination>/home-snapshot-..."`. Configuration, service
credentials and TLS certificates are excluded: back those up separately and
protect this ordinary, unencrypted application data with disk/share encryption.
Restore the entire matching set into a disposable offline installation first;
follow the [offline restore maintenance](https://github.com/Upsylon3/home/blob/main/docs/DEPLOYMENT.md#backups)
before reopening traffic. A shared capture interval does not repair earlier
cross-app inconsistencies or prove historical authenticity.

Keep standard managed Compose containers present (`stop`, not `down`). Snapshot
preflight refuses scaled, paused, restarting or customized containers/overrides.
Recovery waits for originally running containers to finish transient restarts.
Do not run
another lifecycle command, Docker tool or external writer during the operation.
HOME checks container identities/mounts and fingerprints sources before and after
capture; host programs and storage aliases are not a general filesystem lock.

If the command is interrupted, inspect `status` and `logs`, then run
`home.cmd recover-snapshot` or `./home.sh recover-snapshot`. Other actions remain
blocked by `configuration/snapshot-state.json`. Recovery waits for the capture
worker to exit and validates original container identities and storage before
starting them. A failed readiness check keeps the marker for retry. Do not delete
the marker or replace containers to bypass a refusal; resolve the reported writer,
Docker or configuration problem first. Hidden `.home-snapshot-*` leftovers are
incomplete and must never be restored as published sets. Preserve them until
capture has exited; ordinary failures clean their own temporary output.

### Export archives to separate storage

HOME cannot supply another machine or decide where your private backups belong.
Mount storage you control first: for example a NAS share, a folder shared by
another computer, or a removable drive. Create a private destination folder there
and make it accessible to Docker. A different folder on the server's own disk
does not protect against disk failure. HOME cannot prove the physical location
of a mounted path or detect every disconnected-share fallback; check the mount.

After HOME has started and produced successful backups, run one command from
the installation folder. These examples assume the destination already exists:

~~~text
Windows:       home.cmd export-backups "Z:\HOME backups"
Linux:         ./home.sh export-backups "/mnt/backup-nas/HOME"
macOS:         ./home.sh export-backups "/Volumes/Backup/HOME"
~~~

The command copies every published archive currently in `backups/` into a new
`home-backup-export-...` folder. It rereads destination bytes, checks SHA-256,
validates the full compressed stream and restore-checks SQLite databases and
Cloud file references before publishing that folder. A manifest records the
inventory. Failures return a nonzero exit code, leave earlier exports alone and
do not publish a successful export. If local retention removed a selected
archive during export, retry after the backup cycle finishes.

Exports are manual. HOME does not mount shares, save storage credentials, contact
a cloud provider, schedule transfers or delete old destination exports. Leave
space for all retained archives plus scratch for the largest database. Remove
old exports yourself only after checking your recovery needs and another good copy.
Exporting the same history twice creates two complete exports.

Run `verify-backups` with the **specific exported folder**, for example:

~~~text
Windows:       home.cmd verify-backups "Z:\HOME backups\home-backup-export-..."
Linux/macOS:   ./home.sh verify-backups "/mnt/backup-nas/HOME/home-backup-export-..."
~~~

Verification reads the export without changing it and needs local scratch space.
The commands use the installed backup image with networking disabled; they do
not stop HOME or mount installation credentials. Destination paths inside or
containing the installation are refused. Docker must support and have permission
to access the chosen host path; physical network/removable storage still needs
hands-on validation on your platform.
The helper reads existing private, root-owned archives and assigns new export
files to the destination folder's Unix owner. Share permissions must permit this;
Unix mode/ownership settings do not establish Windows ACLs.

These are the existing **per-service snapshots**, with their original timestamps.
An export does not take a new backup, establish a shared cross-service point in
time, or guarantee that every service has a recent archive. Inspect the manifest
and backup logs for coverage/freshness. Configuration, service credentials,
certificates and unarchived live files are excluded: keep their separate protected
backup. Ordinary app data remains unencrypted in these archives; use private,
encrypted destination storage. Checksums detect accidental changes, not a hostile
party changing both an archive and its manifest. Before restoring real data,
perform a disposable restore and follow the repository deployment guide's offline
Core delegation revocation and Monitor identity-reset procedures.

Repeat starts preserve configuration, credentials and data. If setup reports
incomplete state, keep the folder and restore the matching configuration from
backup; it intentionally refuses to overwrite unidentified data. If failure
occurred during a brand-new setup and there is no user data, extract a fresh
download to a different empty folder. Do not delete an unknown data folder.

## Upgrade a downloaded HOME

The upgrade action is available in bundles built after 1.7.0. Run it from the
**new download**, not from the old 1.7.0 launcher. Source-based Compose installations
use the separate import action below.

1. Download a compatible stable release for the same processor. Extract it into
   a different, non-nested private folder. Do not extract over the old HOME,
   start a new installation there, or put it inside the old data directory.
2. Leave enough free space for another complete copy of data, configuration and
   backups, plus the new bundle. Keep an independent protected backup.
3. From the new folder, run one command (quote paths containing spaces):

~~~text
Windows:       home.cmd upgrade "C:\path\to\old-home-folder"
Linux/macOS:   ./home.sh upgrade "/path/to/old-home-folder"
~~~

The launcher checks both folders, stops the old project including optional
services, verifies no containers in that project remain running, copies and
SHA-256 verifies every file, then starts the new services. Identity, account
credentials, access mode, certificates, uploads and backups are retained.
Downgrades, incompatible releases, symlinks/special files, nested folders and
customized Compose deployments are refused. On Windows, paths through junctions
are also refused. Other tools must not write to these folders during upgrade.

Use only the new folder afterward. The original stays unchanged as an **offline
pre-upgrade recovery copy**; do not start or delete it casually. New writes go
to the new folder. Never run both copies or upgrade actions concurrently.

If copying fails, preserve both folders and rerun the same upgrade command.
An incomplete destination refuses to start. If the original changed after a
finished copy, resuming publication is refused: extract another fresh destination
and transfer the original's latest data. A retry after completion does not
recopy older data over new writes; it only starts the transferred installation.

If new services have started, the old folder is now an older snapshot: returning
to it can lose subsequent changes or resurrect revoked background credentials.
Preserve the new folder and follow the offline restore/revocation procedures in
the repository deployment guide before any rollback. Older binaries may also be
incompatible with migrated databases; automatic downgrade/rollback is not offered.
If no new service has ever started, the untouched original remains the latest
copy and can be restarted after ensuring the new project is stopped.

To uninstall, stop HOME first; deleting data is a separate deliberate decision.
Never use `docker compose down -v` as an upgrade. If image cleanup removes a
needed image, run `docker load -i images.tar` in the active bundle folder.

## Import an existing source installation

Use a new bundle containing the import action (the original 1.7.0 download does
not contain it). This supports a complete standard source Compose installation
from 1.7.0 onward, within the destination release's declared compatibility range.
Custom Compose overrides, external volumes, partial stacks and unusual service-secret
quoting need a separate migration. Ordinary account passwords are not restricted.

1. Keep the original checkout, its `homecore/.env`, Docker volumes and backups.
   Containers must still exist so their settings and storage can be verified:
   use `docker compose stop`, not `down`, if stopping beforehand. Do not edit
   settings or start other writers during import.
2. Extract the new bundle into a separate, non-nested private folder. Do not
   start a fresh HOME there first. Allow space for a full data/backup copy.
3. Run from that new folder:

~~~text
Windows:       home.cmd import "C:\path\to\home-source-checkout"
Linux/macOS:   ./home.sh import "/path/to/home-source-checkout"
~~~

The launcher checks the existing containers, their effective settings and the
identity/ownership of every required volume. It stops the source project and
refuses to copy while another container uses that storage. The copy reads the
original volumes read-only, verifies file bytes and retains the original volumes.
No accounts are recreated and service signing credentials are not rotated.

Sign in at **http://localhost:8080** with your existing account. Accounts,
sessions, files, notes/tasks, encrypted Vault records, certificates and backups
are retained. Access starts locally; verify the imported HOME, then use `access`
to enable LAN or public HTTPS again. Never run the old and new installations
together. The new operational installation ID is not a new account identity.

`configuration/core.env` retains shared service credentials; protected
`configuration/source-settings.json` retains the other effective service settings.
Keep both with installation state in configuration backups. Before completion,
`source-import-plan.json` also contains credentials: keep the entire folder private
and never attach these files to an issue. Completion removes its credential payload.

On failure, preserve the original and destination and rerun the same import
action. Incomplete copies refuse to start; completed retries do not overwrite
later writes. A changed source configuration requires a fresh destination.
Once new services have started, the old volumes are a pre-import snapshot:
follow the offline restore/revocation procedures in the repository deployment
guide before returning to them, and preserve any new writes. No automatic
downgrade/rollback or deletion of old volumes is performed.

## Components

HOME uses Docker container images based on Node.js, nginx, Alpine Linux and
Caddy. Source and license information for HOME is at
https://github.com/Upsylon3/home; the matching release tag identifies its code.
Upstream components retain their licenses and notices within their images.
